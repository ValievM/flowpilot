# Конвейер разработки

Задачи живут в GitHub Issues `ValievM/flowpilot`. Исполнители GPT-1, GPT-2, GPT-3 (omp, Codex) берут их через диспетчера, независимый ревьюер (`who:reviewer`) проверяет каждую сдачу до Claude, Claude проектирует, отвечает на вопросы, проверяет и вливает. Владелец смотрит результат и решает только про продукт, деньги, ключи и доступы.

## Роли и зоны
| Роль | Зона | Кольцо проверки (1-й этап) |
|---|---|---|
| GPT-1 | логика: `src/domain`, `src/storage`, интеграции | его проверяет GPT-2 |
| GPT-2 | интерфейс: `src/renderer`, дизайн-система, экраны | его проверяет GPT-3 |
| GPT-3 | инфраструктура, тесты (e2e, снимки), CI, документы, мелкий техдолг | его проверяет GPT-1 |
| Ревьюер | качество кода каждой сдачи: архитектура, паттерны, баги, тесты, перспектива (расширяемость, техдолг); сводка для Claude; только чтение, код и ветки не создаёт | метка `who:reviewer` |
| Claude | архитектура, постановка задач, ответы на вопросы, финальное ревью, слияние | метка `who:claude` |
| Владелец | приёмка руками, решения по продукту | метка `who:owner` |

Все сдачи проходят три этапа: (1) коллега-исполнитель по кольцу (`check`, e2e, мутации, постановка; снимки и e2e остаются зоной исполнителей), (2) независимый ревьюер (`who:reviewer`: архитектура, паттерны, баги, тесты, перспектива), (3) Claude (финальное решение и слияние). Решение владельца 05.10.2026: «хотя пусть у бэков между собой ревью всё таки будет».

## Балансировка очереди (диспетчер)
Диспетчер следит, чтобы роли не простаивали, и переназначает метки `who:` сам, без Claude: (1) проверка `status:review`, которая 15+ минут ждёт занятую роль, передаётся свободному ревьюеру или свободному исполнителю, не автору; (2) готовая задача `status:ready`, которую 30+ минут не берёт занятая роль, переназначается свободной роли. Не трогаются `status:doing`, `who:claude`, `who:owner`, `waiting-owner`, `blocked`; одна задача не чаще раза в час; после каждой правки результат проверяется (`gh issue view --json labels`), в issue остаётся комментарий `[Диспетчер] …`. Простой допустим только если все задачи заблокированы зависимостями, причина записывается в таблице цикла. Правила: `.prompts/dispatcher.md`, раздел «Балансировка».

## Окружение и воспроизводимость процесса
- Исполнители запускают тяжёлые команды через внешнюю обёртку `~/.agent-runner/run <роль> <команда>` (лежит вне репозитория, пишет полный лог в `~/.agent-runner/logs`, лимита одновременных запусков нет).
- Промпты ролей, скрипты диспетчера, автослияния и метрик живут в `.prompts/` основной папки (она в `.gitignore`, живой источник истины). **Снимок для воспроизводимости и ревью:** `docs/process/prompts/` в репозитории; Claude обновляет его при каждом изменении процесса (`cp` файлов из `.prompts/`).

## Уровни риска задач (решение Claude, 05.10.2026)
Метка уровня стоит на каждой новой issue (ставит Claude; по умолчанию `tier:a`, если сомневаешься). Задачи без метки (начатые до введения уровней) доезжают по старым правилам (как `tier:a`).

| Уровень | Что это | Церемония автора | Кто проверяет (по порядку) | Слияние |
|---|---|---|---|---|
| `tier:a` | хранилище, миграции, история и отмена, контракты IPC, команды AI и их применение, безопасность, вложения, экспорт и восстановление | TDD, мутации для каждого теста с логикой, полный `check` | коллега по кольцу → ревьюер → Claude | вручную Claude |
| `tier:b` | экраны и компоненты интерфейса, логика без риска потери данных, e2e-тесты | TDD, **одна** показательная мутация на тестовый файл, полный `check`, для интерфейса `e2e` и снимки | ревьюер → Claude (коллега не нужен) | вручную Claude; **автослияние**, если нет метки `needs-eyes` |
| `tier:c` | CI, документы, конфиги, мелкий техдолг, стили | полный `check`, мутации не нужны | один этап: ревьюер | **автослияние** |

Метка `needs-eyes` стоит на задачах с видимым интерфейсом: снимки против `docs/design/d-screens/` смотрит Claude сам и сливает вручную. Метка `hold` останавливает автослияние.

## Определение готовности задачи (DoR)
Issue можно создавать и ставить `status:ready`, только если: (1) есть тест-кейсы с границами и ошибками; (2) указаны файлы для чтения и номера F/AC; (3) постановка не противоречит сама себе (автор перечитал её перед созданием); (4) размер не больше примерно одного рабочего дня агента и около 400 изменённых строк кода без учёта тестов и эталонов, иначе раздели; (5) стоит метка уровня и, где нужно, `needs-eyes`; (6) зависимости указаны строкой `Зависит от: #N`.

## Самопроверка автора
Перед сдачей автор прогоняет по своему diff чек-лист ревьюера и пишет в отчёте строку «самопроверка по чек-листу: пройдена, найдено и исправлено: …». Короткий свод правил: `docs/process/cheatsheet.md`.

## Автослияние (tier:c и tier:b без needs-eyes)
Скрипт `.prompts/automerge.py` запускается опросом очереди (в фоне, не блокирует) и сливает задачу с меткой `who:automerge` только если одновременно: уровень `tier:c` или `tier:b` без `needs-eyes`; нет метки `hold`; diff не затрагивает файлы, меняющие сами проверки или зависимости (`.github/`, конфиги линтера, TypeScript, Vite, Playwright, Vitest, `package.json` и lock-файл, скрипты, `.prompts/`): такие изменения `check` оценить не может, их сливает только Claude; нет файла-выключателя `.prompts/NO_AUTOMERGE`; последний комментарий ревьюера содержит «Вердикт: ВЛИТЬ» и «ПРОВЕРКА: OK» и **хеш текущего коммита ветки** (позднее запушенное не сливается); ветка сливается с `dev` без конфликтов; CI ветки для этого коммита, если он есть, зелёный (идущий: ждём); `merge-task.sh` проходит полную проверку на слитом результате (для `tier:b` ещё e2e), пушит и закрывает issue. Любое другое условие: ничего не сливается, причина в выводе, жёсткий сбой возвращает issue Claude (`who:claude`) с комментарием. Одно слияние за запуск, слияния сериализованы общим замком с ручными.
**Риски и откат:** ревьюер ошибся, а проверка не поймала (откат: `git revert -m 1 <merge-коммит>` в `dev-wt`, пуш, issue открывается заново); автослияние прошло мимо внимательного взгляда на видимый интерфейс (защита: `needs-eyes`); push после проверки (защита: совпадение хеша). **Выборочный контроль:** раз в день Claude смотрит 1–2 автослитые задачи; найденная проблема = ужесточение условий или метка `hold`. Выключатель: файл `.prompts/NO_AUTOMERGE`.

## Простои и вопросы владельцу
- Вопросы владельцу не блокируют очередь: `WAIT_OWNER` остальную работу не останавливает. У каждого вопроса есть вариант по умолчанию; если ответа нет 12 часов, Claude применяет его и записывает «решение Claude по умолчанию». Диспетчер владельца не спрашивает.
- Монитор очереди Claude при уведомлении об истечении перезапускается первым действием.
- Диспетчер и Claude показывают время простоя: issue на `who:claude` или `who:reviewer` дольше 2 часов без движения это строка «ПРОСТОЙ».
- Сбой записи ревьюера (комментарий или метки не записались): повторить, затем сохранить сводку в `FlowPilot-worktrees/review-notes/<N>.md`, сообщить диспетчеру строкой «СБОЙ GH», Claude подбирает.

## Исполнители и метрики
- Четвёртый исполнитель добавляется, только если в течение дня две и более независимые issue `status:ready` ждут свободного исполнителя, а очередь проверки пустая или короткая. До этого узкое место не мощность, а проверка и зависимости.
- Метрики: `.prompts/metrics.py` раз в день: средний срок от `status:ready` до закрытия, число возвратов, время ожидания Claude и ревьюера; одна строка владельцу.

## Метки
- `who:gpt1|gpt2|gpt3|claude|owner`: чья очередь сейчас.
- `status:ready` (можно брать), `status:doing` (в работе), `status:review` (на проверке), `status:blocked` (вопрос или ждёт зависимостей), `status:waiting-owner`.
- `phase:1` (выпуск 1 «Ручной день»), `phase:2` (выпуск 2 «Помощник и расписание»), `phase:3` (P1 после В2): выпуск плана (`docs/spec/11-implementation-plan.md`). Диспетчер берёт только активные метки.
- `bug`, `chore`, `enhancement`, `decision`.

## Жизнь задачи
1. Claude создаёт issue с полной постановкой (шаблон ниже), `status:ready` или `status:blocked` + строка `Зависит от: #N, #M`.
2. Когда все задачи из `Зависит от:` закрыты, скрипт сам ставит `status:ready`.
3. Исполнитель: `doing` → работа в своём worktree → полный `npm run check` → комментарий СДАНО → `review` и метка проверяющего.
4. Проверяющий GPT: чек-лист, OK → `who:claude`, замечания → вернуть автору.
5. Claude: сверка с постановкой и дизайном, полная проверка на слиянии с `dev`, слияние, закрытие, разблокировка следующих.

## Ветки
`main` (проверенное владельцем) ← `dev` (интеграция, CI) ← задачи `<тип>/<N>-<слово>`. В `dev` и `main` никто, кроме Claude, не коммитит и не пушит. CI запускается на `main`, `dev` и pull request.

## Шаблон задачи (issue)
Первая строка: `**Ветка / Worktree:** <ветка> / <папка> (от dev). Исполнитель GPT-N, размер S/M. Проверяет …`. Затем разделы: Зачем; Что прочитать (файлы); Что сделать; Тест-кейсы (5-10, с границами и ошибками); Мутации; Чего сознательно не делаем; Откат; Готово, когда; Остановиться и спросить. Если есть зависимости, строка `Зависит от: #N`.

## Отчёт исполнителя (комментарий СДАНО)
1. Ветка, worktree, хеши. 2. Что изменено и зачем. 3. Тест-кейсы, красный и зелёный вывод. 4. Мутации. 5. Пути логов `~/.agent-runner/logs/…` с exit=0. 6. Что не проверено. 7. Риски. 8. Вопросы.
