## 2. Работа
Одна задача = своя ветка от `dev` = свой worktree. Чужие ветки и worktree не трогай. 1-3 маленьких коммита, в конце сообщения `Refs #N`. В `dev` и `main` не коммить, не пушь, не мёржь; в origin пушить свою ветку можно (`git push -u origin <ветка>`), чтобы Claude мог её влить.

## 3. Правила разработки (жёсткие)
- Issue это согласованный план, действуй по нему. Противоречит документам или коду, или нужно решение: «[GPT-1] ВОПРОС: …» в issue, метки who:claude + status:blocked (сними who:gpt1 и status:doing), переходи к следующей задаче.
- TDD для логики: красный тест (покажи, что упал по нужной причине), минимальный код, зелёный. Тест-кейсы из issue пиши сразу. Тесты не ослаблять, не удалять, не `.skip`; существующий тест менять только если issue прямо разрешает.
- **Уровень задачи (метка tier:a|b|c на issue, смотри `gh issue view N --json labels`; нет метки = как tier:a, старые правила):** tier:a: красный тест до кода и мутация для каждого нового теста с логикой (сломай код, покажи красный, верни); tier:b: красный тест до кода и **одна показательная мутация на тестовый файл** (самое важное поведение), полный check, для интерфейса e2e и снимки; tier:c: только полный check (мутации не нужны). Строгость от уровня не отменяет лимитов кода, границ слоёв и безопасности.
- Без новых зависимостей, слоёв и паттернов сверх задачи и ADR (`docs/adr/0001-stack.md`); нужна зависимость: спроси. Секретов и личных данных в diff нет. Домен (`src/domain`) не импортирует Electron, React, Node, SQLite: проверяет dependency-cruiser.
- **Стиль кода и ревью обязательны:** `docs/process/code-style.md` и `docs/process/review.md` (прочитай целиком перед первой задачей). Жёстко: никаких «божественных» объектов и файлов; файл до 300 строк, функция до 50, до 4 параметров, сложность до 10, вложенность до 3, один класс на файл; никаких модулей `utils`/`helpers`/`common`/`manager`; нет циклов импортов. Часть проверяет линтер, остальное ревью. Не обходи правила отключением: раздели код.
- UI только на токенах (`tokens.css`), тексты для пользователя русские, сверка с `docs/design/d-screens/` в обеих темах.
- Кончаются токены: доведи шаг до зелёной ветки, сдай отчёт, остановись.

## 4. Тяжёлые команды: только через обёртку (она пишет полный лог; ограничения на одновременные запуски нет)
  ~/.agent-runner/run gpt1 npm run check      # typecheck + lint + stylelint + depcruise + unit
  ~/.agent-runner/run gpt1 npm run e2e        # если трогал интерфейс или сценарии
Во время работы гоняй целевые тесты (например `~/.agent-runner/run gpt1 npx vitest run <путь>`). Перед КАЖДЫМ коммитом полный `npm run check` (и `e2e` для UI). Читай вывод целиком. Красное: не коммить и не сдавай. Обёртка печатает путь лога: прикладывай его к сдаче. Никакого «главного агента», который прогонит проект за тебя, нет.

## 5. Сдача
1. Коммиты в ветке, проверка зелёная, ветка запушена, отчёт по шаблону раздела 9 в файле.
2. На проверку:
  gh issue comment N --repo ValievM/flowpilot --body-file <файл с отчётом, начало «[GPT-1] СДАНО»>
  gh issue edit N --repo ValievM/flowpilot --remove-label "status:doing" --remove-label "who:gpt1" --add-label "who:gpt2" --add-label "status:review"   # tier:a или без метки tier: проверка коллегой по кольцу

  После смены меток обязательно проверь результат: `gh issue view N --repo ValievM/flowpilot --json labels` (имена точные: who:gpt1, who:gpt2, who:gpt3, who:reviewer); ошибка команды оставляет issue без меток, повтори.
3. Цепочка по уровню: tier:a и задачи без метки tier: коллега по кольцу, затем ревьюер, затем Claude. tier:b: ревьюер, затем Claude (для tier:b без метки needs-eyes после «ПРОВЕРКА: OK» слияние автоматическое). tier:c: только ревьюер, затем автослияние. Метка needs-eyes (видимый интерфейс) означает, что снимки смотрит Claude и сливает вручную.
4. Замечания проверяющего правь новым коммитом и сдавай снова. Issue сам не закрывай.

## 5а. Самопроверка перед сдачей (обязательна)
Перед сдачей прогони по своему diff чек-лист ревьюера (`.prompts/reviewer.md`, раздел 1; в репозитории тот же смысл в `docs/process/review.md`): границы слоёв и ADR, лимиты кода (файл 300, функция 50, 4 параметра, сложность 10), нет `utils/helpers/manager` и циклов, ошибки значениями, тесты на ошибки и граничные случаи (а не только счастливый путь), безопасность IPC и данных (`.strict()`, пути только из диалогов main, нет лишних полей), нет лишнего (scope creep), миграции новыми файлами, логи только для сдаваемого коммита при чистом `git status`. Найденное исправь до сдачи. В отчёт добавь строку: «самопроверка по чек-листу: пройдена, найдено и исправлено: …» (или «ничего не найдено» только если реально прочитал свой diff целиком).
