# 10. Формат документов правил

04.10.2026. Проектное решение по делегированию D-20; проверки связаны с D-21. Это отдельный контракт данных, не выбор стека. Названия полей и ограничения ниже — предложение аналитика для будущей реализации.

## Выбор

**JSON + JSON Schema.** JSON хранит правило; JSON Schema описывает разрешённые поля, типы и обязательные значения. Неизвестные поля запрещены, чтобы опечатка не выглядела принятой настройкой. Эти возможности описаны в [официальной документации JSON Schema](https://json-schema.org/understanding-json-schema/reference/object).

TXT можно прикрепить как материал и попросить AI преобразовать в правило. Активным правилом становится проверенный JSON. Формат одинаков для ручного файла, формы приложения и результата чата. Пользователь может импортировать и экспортировать его без AI. Проверяющую схему поставляет приложение; файл правила не выбирает себе произвольную схему или удалённый адрес проверки.

## Минимальная форма

Ниже вымышленный пример, а не реальные предпочтения владельца. `v1` — предложенный идентификатор версии контракта.

```json
{
  "schema_version": "v1",
  "id": "programming-labs",
  "title": "Лабораторные по программированию",
  "scope": {
    "task_type_ids": ["lab"],
    "discipline_ids": ["programming"]
  },
  "rules": [
    {
      "id": "importance",
      "kind": "priority",
      "level": "high",
      "reason": "Без лабораторных нет допуска к экзамену."
    }
  ],
  "guidance": "Если задание неясно, сначала выяснить вопрос у преподавателя."
}
```

| Поле | Смысл и проверка |
|---|---|
| `schema_version`, `id`, `title` | Обязательны. Версия поддерживается; идентификатор уникален; название непустое. Повтор ID — явное обновление существующего документа с показом различий, не создание копии. |
| `scope.task_type_ids` | Обязательный список привязок к существующим типам задач. Пустой список допускается только у неактивного черновика и порождает предупреждение. |
| `scope.discipline_ids` | Необязательный фильтр по дисциплинам. Отсутствие или пустой список означает любые дисциплины внутри выбранных типов. Заполненный — одновременное соответствие типу И дисциплине. |
| `rules` | Обязательный непустой список структурированных правил с уникальными ID внутри документа. |
| `priority` | Разновидность правила: `level` из `high / normal / low`, непустой `reason`. Это важность категории, не окончательный порядок отдельных задач. Шкала — проектное предложение. |
| `time_window` | Другая разновидность: `mode` из `allowed / forbidden / preferred`, непустые дни недели, `start`, `end` в `HH:MM`, явный часовой пояс. Разрешённые/запрещённые интервалы обязательны, предпочтительные — пожелание. Переход через полночь выражается соседними интервалами; пустой интервал отклоняется. |
| `guidance` | Необязательное пояснение обычным текстом. Помогает AI понять контекст, но не отменяет структурированные ограничения и режим подтверждений. |

Ключи не дублируются; пустые строки и неверные значения не принимаются. ID типов/дисциплин стабильны: переименование не разрывает связь. Время отдельной встречи и повторение конкретной задачи хранятся у события/задачи, а не копируются в каждый документ важности. Полный машинный файл схемы будет частью реализации; в этой задаче он не создаётся.

## Проверки и применение

1. **Формат:** синтаксис JSON, версия, поля, типы, перечисления. Ошибка показывает файл, поле и исправление. Неверный импорт сохраняется только как неактивный черновик; прежняя рабочая версия остаётся действующей.
2. **Связи:** неизвестный тип/дисциплина — ошибка активации. Документ без типа — предупреждение «не используется» и действие «Привязать». Тип задач без подходящих активных правил — отдельное предупреждение; ручная работа остаётся доступной.
3. **Согласованность:** дубли ID, неоднозначные правила приоритета одинаковой специфичности, несовместимые структурированные интервалы выявляются до активации. Семантические противоречия свободного текста не обещаем обнаруживать безошибочно.
4. **Область действия:** более конкретное правило дисциплины уточняет приоритет общего типа. Обязательные ограничения объединяются; пустое пересечение означает конфликт, а не молчаливую отмену ограничения. При равной специфичности конфликт нужно разрешить явно. Порядок файлов не задаёт приоритет.
5. **Активация:** импорт, редактирование формы и AI-изменения проходят одинаковую локальную проверку. В чате применяются согласно режиму. Линтер сам не вызывает AI. Уведомление о нерешённой проблеме не повторяется при каждом открытии экрана.
6. **Перестройка дня:** AI получает актуальные применимые правила и может указать, на какой документ опирается. Изменение задач или правил во время подготовки предложения делает его устаревшим; оно не применяется поверх нового состояния. Без правил задача не исчезает и не получает выдуманное обоснование.

При редактировании исходного файла вне приложения рабочие правила не меняются до повторного импорта. Приложение хранит принятую версию; экспорт возвращает её. Неясные последствия удаления типа/дисциплины показываются до действия; оставшиеся непривязанными правила становятся неактивными и видимыми в диагностике.

## Проверяемые сценарии

- **Given** файл с опечаткой в поле, **When** импорт, **Then** указан путь ошибки, активные правила не заменены.
- **Given** документ без привязки, **When** сохранён черновик, **Then** видны предупреждение и действие привязки; AI не применяет его ко всем задачам.
- **Given** два противоречащих структурированных правила одной области, **When** активация нового, **Then** конфликт показан, новая версия не активирована.
- **Given** тип переименован, **When** ручная перестройка, **Then** прежняя привязка сохранена и применимый документ доступен AI.
- **Given** AI подготовил правку правила, **When** режим подтверждений, **Then** до подтверждения действует прежняя версия; в «Авто» валидная правка применяется без дополнительного вопроса.
